Yours, not theirs

One sitting, one win: every room answers only for its owner — plus the full hardening sweep.

⏱ 35–45 minPrerequisites: Lesson 0029 (identity works)Objectives: ownership · CORS · limits
The real problem. Login works — and user A fetches task t9 belonging to user B, because no room ever asks “yours?”. Authentication without authorization is a locked front door with open windows. Today every query grows a WHERE owner, then the sweep: CORS, rate limits, safe errors, secret hygiene.

Chart 93 — Owner check. Strangers get 404, not 403 — confirming “exists but forbidden” hands out an inventory of others' ids.

Source + the 404 rule (click)

Rule: object-level checks answer 404 to non-owners (indistinguishable from missing). 403 stays for role-level denials (“admins only”). Enumeration dies: guessing ids reveals nothing. Implement in SQL (... AND owner check) so the row never even loads.

404 for not-yours · 403 for not-allowed-role · 401 for unknown

Chart 95 — Five locks, one afternoon. None protect data directly — all shrink what attackers can try.

Source + each lock in one line (click)

CORS: allowlist your frontend origin only (it never blocks curl — browsers enforce, attackers don't use browsers). Rate limit: login/register capped per IP (brute force becomes uneconomical). Errors: one sentence out, stacks in logs (0018's lane, unchanged). Secrets: env only, .env ignored, prod values differ. Deps: npm audit in CI, update on alerts. Sources: MDN CORS, OWASP REST.

CORS allowlist · login rate cap · 1-sentence errors · env secrets · npm audit

4 · Live demo: scoped rooms + locks (12 min)

npm install cors express-rate-limit
# service change (the whole ownership story in one clause):
// services/tasks.service.mjs — every query gains the climb:
" ... JOIN projects p ON p.id = t.project_id WHERE p.owner_id = $1 AND ..."
// app.mjs locks (order: chart 51 — locks sit with layers):
import cors from "cors";
import rateLimit from "express-rate-limit";
app.use(cors({ origin: process.env.FRONTEND_URL ?? "http://localhost:5173" }));
app.use("/auth/", rateLimit({ windowMs: 15 * 60e3, limit: 50 })); // 50 login tries / 15min / IP
// rooms: pass req.user.id into every service call; missing row → 404 (never 403)
node -e "/* as user B, knock user A's task id: */ const r = await fetch('http://localhost:3000/tasks/tA1',{headers:{Cookie:'sid='+B}}); console.log(r.status)"
# expected: 404 — indistinguishable from missing. Inventory: protected.
node -e "const r = await fetch('http://localhost:3000/tasks',{headers:{origin:'https://evil.test'}}); console.log('cors:', r.headers.get('access-control-allow-origin'))"
# expected: cors: null — browser would refuse; curl still sees (CORS is browser law)

Why it works: scoping in SQL means unowned rows never load (no code path can leak them); CORS allowlist names the one frontend; the login cap turns password-guessing into centuries.

5 · How this fits TaskFlow

Multi-user TaskFlow is real: register → login → only-your-projects → only-your-tasks, every layer witnessed. Module 7 tests this exact matrix (allowed/denied per role per room); Module 8 re-points CORS at the deployed domain and rotates every secret.

6 · Common mistakes

“Check in code, not SQL.” Loaded the row, then if (task.owner !== me) — one forgotten branch leaks. Fix: scope in the query; unloaded rows can't leak through any branch.
“CORS * with cookies.” Wildcard origin + credentials — browsers refuse the combo, and it invites credential theft. Fix: exact origin allowlist; credentials need named origins, always.
“403 for others' tasks.” Confirms existence (“yes, t9 is real, just not yours”) — id inventory for attackers. Fix: 404 at object level; 403 only for role gates.
