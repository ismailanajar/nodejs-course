JSON + the contract both sides sign

One sitting, one win: you write a mini API contract for one resource and validate its JSON by hand.

⏱ 25–35 minPrerequisites: Lessons 0002–0003Objectives: JSON rules · endpoints · status meaning
The real problem. Your frontend reads task.title — the server sends task.name. Nothing crashes loudly; the screen just shows blank. Every frontend/backend bug of this family is a contract bug: both sides imagined a different shape. Today you learn to write the agreement down first.

1 · The mental model: a restaurant menu

The API is the menu both sides sign: dish names (endpoints), what's inside each dish (shapes), prices (status codes). The frontend orders from the menu; the kitchen cooks to the menu. Nobody improvises — that's the whole discipline:

2 · JSON: six rules, no more

JSON is just text both sides parse identically. Six types exist: string, number, boolean, null, array, object. And six rules:

#RuleWrong → Right
1Double quotes only for keys + strings{'a':1} → {"a":1}
2No trailing commas[1,2,] → [1,2]
3No comments, no functions, no datesdates travel as "2026-10-15" strings
4Top level is an object or arrayour APIs answer with objects holding arrays
5undefined doesn't exist — it gets droppedmissing key ≠ null (explicitly empty)
6Both sides convert: stringify to send, parse to readJSON.stringify(obj) → text → JSON.parse(text)

An endpoint is one menu line: method + path + request shape + response shape + statuses. Our first real menu (Module 4 implements exactly this):

EndpointRequest bodySuccess reply
GET /tasksnone200 + [{ id, title, done }]
POST /tasks{ title }201 Created + the created task
GET /tasks/7none200 + one task, or 404 if unknown

Note 201, not 200, for a creation — statuses are part of the menu, and clients branch on them.

3 · Live demo: stringify, parse, break it (5 min)

Create json-demo.mjs — feel the text/code boundary with your own hands:

// file: json-demo.mjs
const task = { id: 7, title: "Learn JSON", done: false };
const text = JSON.stringify(task);
console.log("sent as text:", text);
console.log("back to object:", JSON.parse(text));
try {
  JSON.parse('{"title":"oops",}');
} catch (err) {
  console.log("broken JSON says:", err.message.split("\n")[0]);
}
node json-demo.mjs
# expected:
# sent as text: {"id":7,"title":"Learn JSON","done":false}
# back to object: { id: 7, title: 'Learn JSON', done: false }
# broken JSON says: Expected double-quoted property name in JSON ... (trailing comma!)

Why it works: the network only carries text — stringify packs your object into text, parse unpacks it. The error message is your proof that rule 2 is enforced by the parser, not by opinion.

5 · Common mistakes

“Single quotes / trailing comma.” JavaScript objects allow them; JSON forbids them. Fix: when hand-writing JSON, use double quotes and no trailing comma — or better, always generate it with JSON.stringify.
“Dates stayed Dates.” JSON.stringify({d: new Date()}) sends an ISO string; parsing won't revive a Date. Fix: agree (in the contract!) on ISO strings and convert explicitly on receipt.
“200 for everything.” Creation returned 200 so the frontend can't tell “created” from “already there”. Fix: 201 on create, 204 on delete with no body, 404 on unknown id — statuses carry meaning.

6 · Practice exercise

  1. On paper, write the contract for POST /tasks: required request keys, one example request, one example 201 reply, and two ways it can fail (with statuses).
  2. Turn your example reply into a JS object in a scratch file, stringify it, parse it back, and confirm the round trip is identical.
  3. Deliberately break the text (trailing comma), parse it, and copy the exact error message under your contract.

Done means: one contract block + one passing round trip + one real parser error quoted verbatim.
