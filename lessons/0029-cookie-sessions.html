MODULE 6 · AUTH + SECURITY · LESSON 2

Prove once, cookie remembers

One sitting, one win: login issues a session cookie; protected rooms know who knocks.

⏱ 35–45 minPrerequisites: Lesson 0028 (login works)Objectives: session · cookie · guard
The real problem. Login works — then the next knock is a stranger again. Re-sending passwords per request is exposure multiplied. Sessions split the job: one strong proof at login, then a random wristband (session id) the server recognizes, revocable in one row-delete.

Chart 90 — Wristband. The cookie holds a random pointer, never identity — the list (server-side) holds the truth. Steal the list? Rotate. Steal a wristband? Revoke one row.

Source + cookie flags (click)

Flags (all three, always): HttpOnly (JS can't read — XSS can't steal), SameSite=Lax (no cross-site rides — CSRF neutered), Secure in prod (https only). Max-Age bounds the party (7 days here). Source: MDN cookies, OWASP sessions.

Set-Cookie: sid=RANDOM; HttpOnly; SameSite=Lax; Path=/; Max-Age=604800 (+Secure prod)

3 · The guard layer (authentication vs authorization)

flowchart TD K7["knock with cookie?"] --> AU["AUTHENTICATION
who are you? → req.user"] AU -- "no session → 401" --> OUT7["stop"] AU -- "user found" --> AZ["AUTHORIZATION
may you? → owner check"] AZ -- "not yours → 403" --> OUT7 AZ -- "yours" --> ROOM["room proceeds"]

Chart 92 — Two questions, in order. 401 = unknown stranger; 403 = known but forbidden. Different questions, different numbers — clients (and attackers) read the distinction.

Source + placement (click)

Guard sits between parser and rooms (chart 51's free slot): public rooms skip it, private rooms require it. Ownership (may-you) lives per-resource in services; identity (who) lives once in the guard.

401 unknown · 403 known-but-no · guard = middleware, ownership = service check

4 · Live demo: wristbands (12 min)

-- file: db/004_sessions.sql
CREATE TABLE sessions (
  id         TEXT PRIMARY KEY,
  user_id    TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  expires_at TIMESTAMPTZ NOT NULL
);
CREATE INDEX ON sessions (user_id);
// sessions + guard (new file: auth.session.mjs)
import crypto from "node:crypto";
import { query } from "./db.mjs";
export async function createSession(userId) {
  const id = crypto.randomBytes(32).toString("hex");
  const { rows } = await query(
    "INSERT INTO sessions(id, user_id, expires_at) VALUES($1,$2,now() + interval '7 days') RETURNING *",
    [id, userId]);
  return rows[0];
}
export function setCookie(res, sid) {
  res.cookie("sid", sid, { httpOnly: true, sameSite: "lax", secure: process.env.NODE_ENV === "production", maxAge: 7 * 864e5, path: "/" });
}
export async function requireUser(req, res, next) {
  const sid = req.cookies?.sid;
  const { rows } = sid
    ? await query("SELECT u.id, u.email FROM sessions s JOIN users u ON u.id=s.user_id WHERE s.id=$1 AND s.expires_at > now()", [sid])
    : { rows: [] };
  if (!rows[0]) return res.status(401).json({ error: "login required" });
  req.user = rows[0];
  next();
}

Why it works: cookie-parser fills req.cookies (unsigned here — randomness is the security, signatures optional); expiry checked in SQL (dead wristbands 401); user DELETE cascades sessions (chart 74's policy, working).

5 · How this fits TaskFlow

Identity flows now; 0030 restricts every room to owners (tasks join projects join users — the family earns its keep); logout + expiry close the loop. JWTs? Deliberately skipped — sessions revoke in one DELETE, tokens need blocklists to match that, and this course picks revocation.

6 · Common mistakes

“Stored user id in cookie.” sid=u1 — forgeable identity. Fix: random pointer only; identity lives server-side, looked up per knock.
“No Secure/HttpOnly.” JS-readable cookie over http — XSS + sniffing steal it. Fix: all three flags (Secure in prod), always — chart 90's line is load-bearing.
“401 vs 403 swapped.” Forbidden-as-401 teaches clients to re-login forever; unknown-as-403 leaks existence. Fix: chart 92 order — who (401) before may-you (403).
