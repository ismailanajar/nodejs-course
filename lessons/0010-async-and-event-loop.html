MODULE 2 · NODE FUNDAMENTALS · LESSON 5

One cook, many orders

One sitting, one win: you can say exactly what await pauses — and what it leaves free.

⏱ 30–40 minPrerequisites: Lessons 0006–0009Objectives: await truth · parallel · loop sketch
The real problem. Your CLI awaits a file read and everything just... waits. Fine for one user. But a server awaits a database for user A while user B knocks — if awaiting blocked the whole process, backends couldn't exist. Today's question: what exactly freezes during await, and what stays open?

1 · The mental model: the counter, not the kitchen

flowchart LR subgraph BLOCK["BLOCKING cook (never do this)"] direction TB B1["take order 1"] B2["stare at oven..."] B3["serve 1, then order 2"] end subgraph NONB["NODE cook (always this)"] direction TB N1["take order 1 → oven"] N2["take order 2 → oven"] N3["serve whoever dings first"] end

Chart 20 — Two cooks. Same single cook in both! Difference: the good cook never stares — waiting happens in the oven (the OS), not at the counter.

Source + the one sentence (click)

The sentence: await pauses your function, never the process — the file read waits inside the OS while Node takes the next order. Blocking code (a giant loop, JSON.parse of megabytes) is staring at the oven: everything queues behind it. Source: Node.js — event loop.

Chart 22 — Gantt proof. Same two waits: ~1000ms stacked vs ~500ms overlapped. Independence is the only requirement.

Source + rule (click)

Rule: independent waits → Promise.all([a, b]); dependent steps (need A's result for B) → sequential awaits. Promise.all rejects fast on the first failure — handle with try/catch around it like any await.

4 · Live demo: feel the overlap + the stare (8 min)

Create overlap.mjs — artificial slow ovens via timers, real stopwatch via Date.now():

// file: overlap.mjs
const oven = (ms, name) =>
  new Promise((done) => setTimeout(() => done(`${name} ding after ${ms}ms`), ms));

let t = Date.now();
console.log("sequential:", await oven(500, "A"), "|", await oven(500, "B"),
  `| total ${Date.now() - t}ms`);
t = Date.now();
console.log("parallel:", await Promise.all([oven(500, "A"), oven(500, "B")]),
  `| total ${Date.now() - t}ms`);
node overlap.mjs
# expected: sequential … total ~1000ms / parallel … total ~500ms — chart 22, alive

Now the stare — one blocking loop freezes even a 0ms timer. Predict before running:

// file: stare.mjs
setTimeout(() => console.log("timer: I should be instant..."), 0);
const end = Date.now() + 1500;
while (Date.now() < end) {} // staring at the oven for 1.5s
console.log("loop done — only NOW does the timer speak");
node stare.mjs
# expected: 1.5s silence, then BOTH lines — the 0ms timer waited behind your loop.
# One runner, proven: no JS runs while JS runs.

Why it works: timers hand their wait to the OS (chart 21's loop serves them); the busy loop never yields, so the loop can't reach the dinged timer. Servers die exactly this way — never loop big in a handler (Module 4 will remind you).

5 · How this fits TaskFlow

CLI barely needs this (one user, one breath). Servers live by it: while Postgres thinks for user A, your handler for user B runs — thousands of overlapping dings, one process, tiny memory. Every future “why is the API slow?” splits into chart-20 halves: slow ovens (DB, network — scale/parallelize) vs staring cooks (blocking code — delete it).

6 · Common mistakes

“await in a loop for independent reads.” Five files read one-by-one = 5× time. Fix: map to promises + one Promise.all — chart 22's bottom half.
“await pauses everything.” It pauses your function; timers/files/network of others proceed. Fix: re-read chart 21 — only your continuation sleeps.
“Sync crypto/hash in a handler.” Preview of a Module 6 landmine: password hashing has sync AND async forms — the sync form stares. Fix: always the async form in servers; you'll be graded on this later.
