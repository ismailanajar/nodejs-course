MODULE 5 · DATABASES + SQL · LESSON 3

Tables that know each other

One sitting, one win: users own projects, projects hold tasks — linked by keys, read with JOINs.

⏱ 35–45 minPrerequisites: Lesson 0023 (SQL verbs)Objectives: FK · 1-N · JOIN
The real problem. One tasks table can't say whose task it is — add a owner_name column and renames corrupt history, duplicates bloat, deletes orphan rows. Related facts belong in related tables, stitched by keys the database enforces. That's the “relational” in relational databases.

1 · The mental model: family registry

Source + FK law (click)

Law: a foreign key value must exist (or be NULL) in the parent — inserting a task for project nope is refused by the building. Orphans become unrepresentable, not merely unlikely. Source: PG foreign keys.

project_id TEXT REFERENCES projects(id) -- the stitch, enforced

Chart 73 — Stitching on read. Storage stays split (no duplication); questions stitch on demand via key equality.

Source + the ON sentence (click)

... FROM tasks JOIN projects ON tasks.project_id = projects.id — ON states the stitch (keys equal), WHERE still filters, and prefixes (tasks.title) disambiguate shared names. INNER JOIN drops unmatched rows; unmatched tasks (NULL project) need LEFT JOIN (0025's drill).

SELECT tasks.title, projects.name FROM tasks
JOIN projects ON tasks.project_id = projects.id
WHERE tasks.done = false;

4 · Live demo: family + stitch (12 min)

Migration db/002_family.sql — new tables, then the stitch column (tasks already exists):

-- file: db/002_family.sql
CREATE TABLE users (
  id    TEXT PRIMARY KEY,
  email TEXT NOT NULL UNIQUE
);
CREATE TABLE projects (
  id       TEXT PRIMARY KEY,
  owner_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  name     TEXT NOT NULL
);
ALTER TABLE tasks ADD COLUMN project_id TEXT REFERENCES projects(id) ON DELETE CASCADE;

# expected: violates foreign key "tasks_project_id_fkey" — the building refuses. Orphans: impossible.
SELECT tasks.title, projects.name FROM tasks
JOIN projects ON tasks.project_id = projects.id;
# expected: Learn JOINs | Course — stitched, no duplication stored
DELETE FROM users WHERE id = 'u1';
SELECT * FROM projects; SELECT * FROM tasks;
# expected: both empty — CASCADE carried the delete down the family. Deliberate power.

Why it works: UNIQUE on email prevents double registration (Module 6 leans on this); the demo ends empty by design — re-seed after, or keep a db/seed.sql (next lesson's habit).

5 · How this fits TaskFlow

The schema is final-shaped: users → projects → tasks. 0025 queries it from Node (parameterized JOINs); Prisma (0026) declares these three models and the client stitches with include. Auth (Module 6) hangs ownership checks on these same keys.

6 · Common mistakes

“Name instead of id in child.” project_name on tasks — renames corrupt history. Fix: children carry parent keys, JOINs fetch names at read time.
“JOIN multiplies rows, panic.” One task × one project = one row; but joining two 1-N children fans out (m×n). Fix: expect fan-out, aggregate or split queries — Prisma's include handles this for you later.
“CASCADE everywhere.” Deleting a user vaporizes years of tasks — correct here, catastrophic for audit data. Fix: default RESTRICT; CASCADE only where “parent gone = children meaningless” is truly the rule.
