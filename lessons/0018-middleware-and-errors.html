Layers you control

One sitting, one win: every knock gets logged, bad JSON gets a JSON answer, and errors land in one place.

⏱ 30–40 minPrerequisites: Lesson 0017 (Express hello)Objectives: use/order · next · error lane
The real problem. Two embarrassments ship in 0017's app: corrupt JSON answers in HTML (a JSON API speaking prose), and every handler repeats its own try/catch. Both come from one missing idea: code that runs around handlers — before them, after them, and when they throw.

Chart 50 — The conveyor. Every knock walks every layer in registration order; the error lane runs only when something throws. Order is behavior.

Source + the next() contract (click)

Contract: a layer either replies (journey ends) or calls next() (journey continues). Forget both and the knock hangs — lesson 0012's missing-end, wearing a suit. Error layers take four args (err, req, res, next); Express spots the arity and routes throws there. Source: Express — middleware, error handling.

Chart 51 — Standard stack. Five lines, always this order: observe → parse → decide → catch-unknown → catch-broken. Memorize the order; it never changes.

Source + placement law (click)

Law: loggers first (see everything), parsers before rooms (rooms need bodies), 404 after rooms (only the unmatched fall through), error lane last (catches all throws including parser explosions — that's what fixes the HTML surprise).

  A2["logger"] --> B2["parser"] --> C2["rooms"] --> D2["404"] --> F2["errors"]

4 · Live demo: civilized app (10 min)

Upgrade app.mjs — three additions around the rooms (rooms unchanged):

// 1 — logger FIRST (sees everything, measures time):
app.use((req, res, next) => {
  const t = Date.now();
  res.on("finish", () => console.log(`${req.method} ${req.url} → ${res.statusCode} (${Date.now() - t}ms)`));
  next();
});
app.use(express.json());

// ... rooms here (unchanged) ...

// 2 — 404 trapdoor AFTER rooms:
app.use((req, res) => res.status(404).json({ error: `no such room: ${req.method} ${req.url}` }));

// 3 — error lane LAST (four args!):
// eslint-disable-next-line no-unused-vars
app.use((err, req, res, next) => {
  console.error(err); // private truth, server-side only
  const status = err.status ?? err.statusCode ?? 500;
  const message = status === 500 ? "something broke" : err.message || "bad request";
  res.status(status).json({ error: message });
});
node app.mjs
node -e "const r = await fetch('http://localhost:3000/tasks',{method:'POST',headers:{'content-type':'application/json'},body:'{oops'}); console.log(r.status, await r.json())"
# expected: 400 { error: ...JSON... } — JSON crime, JSON answer. Surprise fixed.
node -e "const r = await fetch('http://localhost:3000/nope'); console.log(r.status, await r.json())"
# expected: 404 { error: 'no such room: GET /nope' } — trapdoor speaks menu language

Why it works: the parser's throw lands in the error lane (status 400 rides along on the error object); unknown paths fall past rooms into the trapdoor; the logger's finish listener fires after the reply leaves — observation without interference.

5 · How this fits TaskFlow

Every future layer slots into chart 51 without moving residents: auth checks (Module 6) sit between parser and rooms; Zod validation (0019) lives inside rooms or as room-specific layers. The error lane is finished — it will barely change for the rest of the course.

6 · Common mistakes

“Error lane never fires.” Three args (err, req, res) — Express reads it as a normal layer. Fix: four args exactly; the unused next is structural, keep it (hence the lint comment).
“404 trapdoor eats real rooms.” Registered before the rooms. Fix: chart-51 order — trapdoor after rooms, error lane after trapdoor. Order is behavior.
“Leaked stack to client.” Sent err.stack in the JSON for debuggability. Fix: stacks stay in server logs; clients get one sentence. Attackers read error output like documentation.
