Pools and parameters

One sitting, one win: your API reads Postgres with injection-proof queries over a shared pool.

⏱ 35–45 minPrerequisites: Lesson 0024 (schema lives)Objectives: pool · $1 · migrations
The real problem. SQL is text — and text built by gluing user input is a loaded weapon (' OR '1'='1 logs in as anyone). Plus opening a fresh database connection per knock costs ~30ms of handshake. Two mechanisms fix both: never concatenate input, never handshake twice.

1 · The mental model: taxi fleet, sealed envelopes

Chart 75 — Fleet, not ownership. Knocks borrow a ready connection and return it; handshakes happen once at startup. Ten fleet cars serve hundreds of sequential riders.

Source + sizing (click)

Create one Pool at startup, share it, never close per request. Size ≈ CPU cores × 2 for this course (defaults fine); exhaustion surfaces as timeouts, not errors — the cue to look at slow queries, not bigger pools. Source: node-postgres docs.

const pool = new Pool({ connectionString: process.env.DATABASE_URL });

2 · Parameters: code and data travel separately

flowchart TD BAD["glue: `... id='${id}'`
input BECOMES code → injection"] GOOD["parameter: WHERE id=$1, [id]
input stays DATA → safe"] GOOD --> DB7[("plan once
values bound later")]

Chart 76 — The only rule. $1, $2… mark holes; the values array fills them as pure data. User text can never become SQL again — injection becomes unrepresentable.

Source + demo wound (click)

Glue id = 'x' OR '1'='1 into text and the WHERE matches everything (login bypass, data dump). Parameterize the same input and Postgres compares the literal weird string — zero rows, correct. This one habit is 90% of backend data security.

pool.query("SELECT * FROM tasks WHERE id = $1", [id]); -- safe, always

Swap db.mjs storage (interface unchanged — services don't notice):

// file: db.mjs (Postgres edition — same exports: load/save stay for CLI compat)
import pg from "pg";
const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL });
export const query = (text, params) => pool.query(text, params);
// services now use query() — e.g. list:
export async function listTasks({ done, limit = 10, offset = 0 }) {
  const conds = [], params = [];
  if (done !== undefined) { params.push(done === "true"); conds.push(`done = $${params.length}`); }
  const where = conds.length ? `WHERE ${conds.join(" AND ")}` : "";
  params.push(limit, offset);
  const { rows } = await query(
    `SELECT * FROM tasks ${where} ORDER BY created_at DESC LIMIT $${params.length - 1} OFFSET $${params.length}`,
    params);
  return rows;
}
node -e "const {query} = await import('./db.mjs'); console.log((await query('SELECT count(*) AS n FROM tasks')).rows)"
# expected: [ { n: '3' } ] — counts come back as TEXT (pg quirk: parse numerics yourself)
node -e "const {query} = await import('./db.mjs'); console.log((await query(\"SELECT * FROM tasks WHERE id = \$1\", [\"x' OR '1'='1\"])).rows)"
# expected: [] — the attack string compared literally. Injection: dead on arrival.

Why it works: placeholders are positional ($1 = first array item); dynamic SQL still builds structure (WHERE/ORDER from allowlists) while values always ride parameters. ORDER BY direction must come from an allowlist (asc/desc enum) — never a parameter (identifiers can't be bound).

6 · Common mistakes

“New Pool per request.” Handshake storm, port exhaustion. Fix: one pool per process, created at startup, shared everywhere.
“Interpolated ORDER BY.” ORDER BY ${sort} — identifiers can't bind, injection reopens. Fix: allowlist map ({title:'title',created:'created_at'}[sort] ?? 'created_at').
“Count is a string?!” pg returns numerics/ints as text (precision safety). Fix: Number(row.n) at the boundary — or set pg types parsers once, deliberately.
