Where does your request actually go?

One sitting, one win: you read any URL like an address and you know exactly what localhost and a port mean.

⏱ 25–35 minPrerequisites: Lesson 0002 (request vs response)Objectives: URL parts · localhost · ports · dev vs prod
The real problem. Your code says fetch("/api/tasks") and it works on your laptop — then a friend opens it on their phone and everything breaks. Or you see “localhost refused to connect” and have no idea which half is wrong. Both mysteries are addressing problems, and after today you solve them in seconds.

1 · The mental model: a postal address

A URL is a postal address with four levels, biggest to smallest:

flowchart LR U["URL
full address"] --> H["HOST
which building?"] H --> P["PORT
which door?"] P --> R["PATH + QUERY
which room, which note?"] R --> S["Server handler
delivers the reply"]

Diagram D — URL to handler. Left to right = big to small. Each level answers one question.

How to read + walkthrough (click)

How to read: boxes are narrowing-down steps; follow left to right. The request dies at the first level that matches nothing — that tells you who to blame.

Walkthrough for http://localhost:3000/tasks?done=false: ① host localhost = “this same laptop” ② port 3000 = “door 3000 — the API's door” ③ path /tasks = “the tasks room” + query done=false = “only unfinished, please”. Wrong host → network error. Wrong port → “refused to connect”. Wrong path → 404.

Takeaway: read every URL failure right-to-left blame order: path (404?) → port (refused?) → host (DNS/network?). Source: MDN — What is a URL.

2 · The five parts of a URL (only five — that's all)

PartExamplePlain meaning
Protocolhttp:// / https://How to speak: plain (dev) vs encrypted (the real web). Prod is always https.
Hostlocalhost / api.taskflow.appWhich machine. localhost = “this laptop I'm on now” — nothing more.
Port:3000 / :5173Which door on that machine. One door = one server process. Browsers hide :80 and :443 (the defaults).
Path/tasks/7Which thing on that server. Leading slash = “from the root”.
Query?done=false&page=2Filters/options: key=value pairs joined by &. Never identifies — only filters.

Two facts that prevent real bugs: the fragment (#section) is never sent to the server — the browser keeps it. And fetch("/api/tasks") with a path-only URL reuses today's host + port — which is why it works in dev and breaks the moment frontend and API live on different machines (Module 8 fixes that with proxy/CORS config).

3 · localhost and ports, precisely

localhost is a nickname for “this machine” (address 127.0.0.1). Your laptop's localhost is YOUR laptop; your friend's phone has its OWN localhost. So “open localhost:3000 on your phone” can never work — the API lives on your laptop's door, not theirs.
Port is a number 1–65535 naming one listening server. Conventions you'll meet weekly: 3000 API (Node), 5173 Vite dev frontend, 5432 PostgreSQL, 80/443 real websites. Two servers can't share one door — the second crashes with EADDRINUSE (Module 3 makes you trigger this on purpose).
Dev vs production server. Dev = your laptop, sloppy and verbose (auto-reload, stack traces, http). Production = a rented machine open to the internet (https, secrets from env vars, logs instead of console peeking). Same code, different discipline — Module 8 does the move.

4 · Live demo: dissect URLs + meet “refused to connect” (5 min)

A — dissect any URL with zero dependencies. Create url-demo.mjs — the global URL class does the parsing:

// file: url-demo.mjs
const u = new URL("http://localhost:3000/tasks/7?done=false#top");
console.log("protocol:", u.protocol);
console.log("host:", u.hostname);
console.log("port:", u.port);
console.log("path:", u.pathname);
console.log("query:", u.search);
console.log("hash:", u.hash, "(stays in browser — never sent)");
node url-demo.mjs
# expected:
# protocol: http: / host: localhost / port: 3000
# path: /tasks/7 / query: ?done=false / hash: #top (stays in browser — never sent)

B — see the most common backend error on demand. Nothing listens on port 9999, so this fails fast — read the failure, it's your future debugger:

// file: refused-demo.mjs
try {
  await fetch("http://localhost:9999/health");
} catch (err) {
  console.log("name:", err.constructor.name);
  console.log("cause:", err.cause?.code ?? "(see message)");
  console.log("meaning: no server behind door 9999 — start it or fix the port");
}
node refused-demo.mjs
# expected: cause ECONNREFUSED — the signature of “wrong port / server not started”

Why it works: demo A proves a URL is just structured text you can split. Demo B proves “refused” always means host-reached-but-nobody-behind-that-door — never a code bug in your handler.

5 · How this fits TaskFlow

From Module 3 on, your world is two doors: frontend on localhost:5173, API on localhost:3000, Postgres behind localhost:5432 (no HTTP — raw database protocol). Every “it doesn't connect” moment for the rest of the course is answered by §1's blame order: path → port → host.

6 · Common mistakes

“It works on my laptop but not their phone.” You hardcoded localhost. Fix: phone needs your laptop's LAN address (e.g. http://192.168.1.20:3000) or a deployed URL — localhost never leaves its own machine.
“Port in use” crash. An old server still holds the door (EADDRINUSE). Fix: kill the old process, don't just open a new terminal and retry.
“Query identifies the item.” /tasks?id=7 instead of /tasks/7. Works by accident, breaks caching and REST conventions. Fix: path identifies, query filters — no exceptions in this course.

7 · Practice exercise

  1. Run demo A with these three URLs: https://api.taskflow.app:443/projects?page=2, http://localhost:5173/, http://localhost:3000/tasks/7?done=false#top. Write the five parts of each.
